# Hermes Agent adoption review

**Date:** 2026-08-04  
**Scope:** official Hermes repository sources and the local Codinal repository only.

## Recommendation

Do not vendor or replace Codinal’s runtime with Hermes. Keep Hermes an optional external integration, with ACP as the preferred boundary if Codinal wants to launch Hermes as an alternate agent backend; use MCP only for tool/service interoperability. This preserves Codinal’s local-first coding product and its existing security/session ownership while allowing selective access to Hermes’ messaging, remote terminal, skill, memory, and scheduling features.

## What Hermes actually provides

Hermes is a complete Python agent application, not a small agent-loop library. Its README describes a terminal UI, a multi-platform messaging gateway, persistent/searchable memory, self-created and self-improving skills, cron delivery, parallel subagents, multiple terminal backends, and trajectory-generation tooling ([Hermes README](https://github.com/NousResearch/hermes-agent/blob/main/README.md)). The repository layout confirms separate `agent`, `gateway`, `cron`, `skills`, `providers`, `acp_adapter`, and MCP-related code ([repository tree](https://github.com/NousResearch/hermes-agent/tree/main)).

Its extension surfaces are deliberately process/application-level:

- **Skills:** filesystem-discovered skills, including external skill roots and progressive loading; Hermes’ skill utility owns scanning/parsing and its config has a dedicated `skills` area ([`agent/skill_utils.py`](https://github.com/NousResearch/hermes-agent/blob/main/agent/skill_utils.py), [`hermes_cli/config.py`](https://github.com/NousResearch/hermes-agent/blob/main/hermes_cli/config.py)).
- **Tools/MCP:** Hermes can connect MCP tools and can itself expose a stdio MCP server for messaging/session operations ([`mcp_serve.py`](https://github.com/NousResearch/hermes-agent/blob/main/mcp_serve.py), [`tools/mcp_tool.py`](https://github.com/NousResearch/hermes-agent/blob/main/tools/mcp_tool.py)).
- **ACP:** `hermes-acp` starts an Agent Client Protocol stdio server; stdout is reserved for ACP JSON-RPC, while logging goes to stderr. The adapter creates Hermes sessions and bridges tool permissions into ACP ([`acp_adapter/entry.py`](https://github.com/NousResearch/hermes-agent/blob/main/acp_adapter/entry.py), [`acp_adapter/server.py`](https://github.com/NousResearch/hermes-agent/blob/main/acp_adapter/server.py), [`acp_adapter/permissions.py`](https://github.com/NousResearch/hermes-agent/blob/main/acp_adapter/permissions.py)).
- **Plugins/subagents:** the source exposes plugin-safe subagent lifecycle objects, but they still launch Hermes-managed child sessions and toolsets rather than a narrow embeddable callback interface ([`agent/subagent_lifecycle.py`](https://github.com/NousResearch/hermes-agent/blob/main/agent/subagent_lifecycle.py)).

## Fit with Codinal

Codinal already assigns the core responsibilities Hermes would duplicate: the Rust GPUI desktop owns launch and runtime integration; the Python sidecar owns the authenticated loopback control plane, sessions, provider routing, TurnEngine, MCP, tool registry, sandbox, and Git worktrees ([`desktop/README.md`](../../desktop/README.md), [`runtime/README.md`](../../runtime/README.md)). Its accepted architecture explicitly makes **harness = policy/control** and **runtime = mechanics**, with a `PermissionEngine` chokepoint, manifest-bound tools, per-session worktrees, Keychain-backed secrets, and a local-only v1 scope ([ADR-0001](../decisions/0001-codinal-foundation.md)).

| Area | Hermes | Codinal consequence |
|---|---|---|
| Agent loop/providers | Broad, mature application with many providers and toolsets ([`pyproject.toml`](https://github.com/NousResearch/hermes-agent/blob/main/pyproject.toml)) | Mostly duplicate Codinal’s provider contract/router and TurnEngine; little safe code-level reuse. |
| Skills | Strongest overlap: filesystem skills, bundles, external roots | Reuse the compatibility idea/configuration, not Hermes’ scanner as a second skill SSOT. Codinal’s harness already owns `~/.agents/skills` and records Hermes external-dir discovery ([`MANIFEST.md`](../../MANIFEST.md), [`hosts.yaml`](../../harness/config/hosts.yaml)). |
| MCP | Useful interoperability seam; Hermes can consume and serve MCP | A candidate adapter, subject to Codinal’s existing approval, HTTPS/loopback, stdio environment, manifest, and session-idle rules ([`runtime/mcp/service.py`](../../runtime/mcp/service.py)). |
| ACP | Best alternate-agent seam: one stdio process, structured session/events/permission bridge | Plausible optional backend if Codinal implements an ACP client. It does not make Hermes’ internal state, tools, or memory native to Codinal. |
| Security | Hermes has approvals and tool guardrails, but its loop/config/tool execution remain Hermes-owned; guardrails document warnings by default and opt-in hard stops ([`agent/tool_guardrails.py`](https://github.com/NousResearch/hermes-agent/blob/main/agent/tool_guardrails.py)) | Do not let Hermes bypass Codinal’s manifest, `PermissionEngine`, Seatbelt sandbox, Keychain secret boundary, or Git worktree/apply-back flow. |
| Product surface | Messaging gateway, cron, remote environments, memory, voice, dashboard | Valuable only if Codinal later expands beyond its stated lean coding MVP; currently out-of-scope duplication ([ADR-0001](../decisions/0001-codinal-foundation.md)). |

## Licensing, dependency, and runtime implications

Hermes is MIT-licensed ([`LICENSE`](https://github.com/NousResearch/hermes-agent/blob/main/LICENSE)); that is compatible with Codinal’s MIT decision, assuming normal attribution and separate review of transitive/optional dependency licenses ([ADR-0001](../decisions/0001-codinal-foundation.md)). License compatibility is therefore not the blocker.

The operational cost is material. Hermes requires Python `>=3.11,<3.14`, has a large exact-pinned core dependency set, numerous provider/messaging/terminal extras, and a lazy-install mechanism ([`pyproject.toml`](https://github.com/NousResearch/hermes-agent/blob/main/pyproject.toml), [`tools/lazy_deps.py`](https://github.com/NousResearch/hermes-agent/blob/main/tools/lazy_deps.py)). Its supported install provisions `uv`, Python 3.11, Node.js, ripgrep, ffmpeg, and platform-specific terminal/runtime pieces ([Hermes README](https://github.com/NousResearch/hermes-agent/blob/main/README.md)). Codinal instead targets a signed/notarized macOS app with embedded Python 3.12 and a pinned runtime lock ([ADR-0001](../decisions/0001-codinal-foundation.md), [`runtime/requirements.in`](../../runtime/requirements.in)). Embedding Hermes would mean reconciling two Python dependency graphs, packaging/signing another application surface, and deciding who owns config, secrets, sessions, updates, and child processes. Running `hermes-acp` externally avoids most of that but still requires a separately installed Hermes environment and its own `~/.hermes` state ([`hermes_constants.py`](https://github.com/NousResearch/hermes-agent/blob/main/hermes_constants.py), [`acp_adapter/entry.py`](https://github.com/NousResearch/hermes-agent/blob/main/acp_adapter/entry.py)).

## Concrete decision

1. **Reject full reuse/fork/embedding for Codinal v1.** It duplicates the runtime and conflicts with Codinal’s ownership and distribution boundaries.
2. **Permit a future optional Hermes ACP backend.** Define an explicit subprocess lifecycle, workspace mapping, event translation, approval policy, cancellation, and failure semantics; keep Codinal’s bearer/auth, secrets, worktree, and apply-back controls authoritative.
3. **Permit MCP adapters where there is a concrete use case.** Treat Hermes-connected tools as external tools, never as an implicit trust upgrade.
4. **Do not add Hermes’ memory, skill, cron, or gateway state to Codinal’s SSOT.** If those features become product requirements, integrate them as separately owned capabilities with migration and threat-model work.

**Bottom line:** Hermes is a capable companion application and a useful protocol peer, but not a good internal foundation for Codinal. The highest-value reuse is the ACP/MCP boundary; the lowest-risk near-term action is no code change.

## Dated evidence addendum — 2026-08-04

1. **Hermes is genuinely mature as an application, not as a drop-in loop dependency.** The official GitHub API snapshot reports 224,855 stars, 43,561 forks, 17,399 commits shown on the repository page, and `archived: false`; these are strong adoption/activity signals, but they measure repository interest, not compatibility with Codinal’s ownership model. [GitHub repository API](https://api.github.com/repos/NousResearch/hermes-agent), [repository](https://github.com/NousResearch/hermes-agent).

2. **Release cadence is current but also signals ongoing change.** The latest official release is Hermes Agent v0.20.0, released 2026-08-03; the release notes describe a very broad surface expansion (voice, A2A, webhooks, desktop plugins, approvals, and tool-loop changes). That justifies using Hermes as a maintained external product, not freezing its internals into Codinal. [Latest release](https://github.com/NousResearch/hermes-agent/releases/latest).

3. **The architecture overlaps Codinal at the core.** Hermes’ README presents one product containing the TUI, messaging gateway, persistent memory/session search, skills, cron, subagents, and multiple terminal backends. Codinal already has a policy-bound `TurnEngine`, provider router, sessions, events, tool registry, MCP transport, sandbox, and Git/worktree services. This is replacement-level overlap, not a missing utility that Hermes uniquely supplies. [Hermes README](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/README.md), [Codinal runtime README](../../runtime/README.md), [Codinal foundation ADR](../decisions/0001-codinal-foundation.md).

4. **ACP is the cleanest integration seam, but it is a process boundary.** Hermes documents ACP as JSON-RPC over stdio for external hosts and exposes session creation, prompts, streaming updates, tool calls, permissions, fork, cancel, and authentication. The ACP server is implemented in `acp_adapter/`, while the same Hermes `AIAgent` remains underneath; this enables an optional backend but does not make Hermes’ loop, state, tools, or memory native to Codinal. [Programmatic integration](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/developer-guide/programmatic-integration.md), [ACP server source](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/acp_adapter/server.py), [ACP entrypoint](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/acp_adapter/entry.py).

5. **ACP appears usable, but “stable” should not be overclaimed.** Hermes’ official ACP guide says it is used with VS Code, Zed, and JetBrains, and provides `hermes acp --check`; the current package still treats ACP as an optional extra and the release stream is actively changing. No official source reviewed here promises long-term wire/API stability, so Codinal should pin and conformance-test an ACP version before shipping an adapter. [ACP feature guide](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/acp.md), [Hermes package metadata](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/pyproject.toml).

6. **ACP does not remove ownership and security conflicts.** The official ACP guide says the underlying `AIAgent` keeps Hermes’ normal persistence/logging paths and that ACP session list/load/resume/fork are scoped to the running ACP server process. Codinal must therefore retain authority over its bearer-authenticated control plane, `PermissionEngine`, Seatbelt sandbox, Keychain secrets, session worktrees, and Apply-back flow rather than treating Hermes approvals as a substitute. [ACP feature guide](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/acp.md), [Codinal runtime README](../../runtime/README.md), [Codinal foundation ADR](../decisions/0001-codinal-foundation.md).

7. **MCP is complementary, not a reason to adopt Hermes.** Hermes can consume MCP and expose Hermes conversations through an MCP server; Codinal already has an MCP service that turns discovered remote tools into manifest-declared `external` actions requiring approval. Integrate a concrete Hermes capability through that existing policy boundary only when needed. [Hermes CLI/MCP reference](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/reference/cli-commands.md), [Codinal MCP implementation](../../runtime/mcp/tools.py), [Codinal runtime README](../../runtime/README.md).

8. **Licensing is permissive; packaging and distribution are the real costs.** Hermes is MIT-licensed, but its current metadata requires Python `>=3.11,<3.14`, uses a substantial exact-pinned dependency set, and includes optional provider/platform extras. Codinal’s accepted distribution is a signed/notarized macOS app with embedded Python 3.12 and its own pinned runtime; embedding Hermes would create a second dependency/config/state/update boundary. [Hermes LICENSE](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/LICENSE), [Hermes package metadata](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/pyproject.toml), [Codinal foundation ADR](../decisions/0001-codinal-foundation.md).

**Recommendation:** Do not replace Codinal’s own agent loop or vendor Hermes for v1. Keep Codinal’s loop and policy ownership. If a user-facing need justifies Hermes’ broader capabilities, add a version-pinned, conformance-tested optional ACP subprocess backend with explicit workspace mapping, event/permission translation, cancellation, failure handling, and state isolation. Treat Hermes MCP integration as ordinary external tooling. The current evidence justifies optional interoperability, not making Hermes a Codinal prerequisite.
